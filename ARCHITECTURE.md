# Architecture Specification: CloudCanvas

**Author / Organization**: NeoTec, LLC, Richard Christopher

> **Repository scope.** This repository is the **core engine only** (`engine/`, `graphics/`,
> `pins/`, `particles/`, `index.js`). This document is the full architectural spec for the whole
> CloudCanvas system and therefore also describes two things that now live in **sibling
> repositories** and are *not* present here:
> - The base widget kit and pre-built component library (`lib/`, `cloudcanvas/lib`,
>   `cloudcanvas/components`, `cloudcanvas/sandbox`) → **[NeoTecDigital/cloudcanvas-lib](https://github.com/NeoTecDigital/cloudcanvas-lib)**.
> - The interactive playground, harness and site builder (`examples/`, `examples/website-sandbox*`)
>   → **[NeoTecDigital/cloudcanvas-site](https://github.com/NeoTecDigital/cloudcanvas-site)**.
>
> The filesystem hierarchy and any section below that references `lib/…` or `examples/…` paths
> describes the original monorepo layout; those paths resolve in the sibling repos, not in this one.

A minimalist, embeddable client-side graphical user interface (GUI) library that treats HTML `<div>` elements as interactive canvas objects ("Pins").

The core Pin model is stripped down to its essential foundation: **Traits**, **Contents** (`Map<string, Object>`), and **Vectors** (`float[]`). All behavioral, spatial, interaction, display, physical capabilities, focus handling, and scoping are abstracted into composable, programmable **Traits**.

## 2. Tech-Agnostic Spec Sheet

### 2.1 Minimal Pin Base Model
- **Role**: Pure base container representing a canvas entity. `Pin extends EventTarget`.
- **Base Components**:
  - **Traits**: A composable set of active `PinTrait` instances defining behaviors and rendering capabilities; at most one trait per name.
  - **Contents**: A `Map<string, Object>` storing key-value object payloads.
  - **Vectors**: An array of `float` values representing magnitude, gradient, orientation, velocity, or directional pointers (held by the Pin's `PinParticle`).
  - **DOM Element**: A `<div>` with a fixed two-child structure - `.cloudcanvas-pin > .cloudcanvas-pin-content + .cloudcanvas-pin-scope`. Display traits only ever write into the content node, so nested child Pins in the scope node survive every content update.
  - **Hierarchy**: `parent` pointer and `children: Set<Pin>` for nested scopes.
  - **Activation**: `active: boolean` plus a `reload` strategy (`active` | `persistent` | `lazy`); `lazy` is a derived getter over `reload === 'lazy'`.
- **Construction-time invariants**: `utility` (a null Pin - machinery, no element, filtered out of every caller-facing query) and `selectableText` (§2.12) are read once, at construction, because both are written onto the element at setup and neither is meaningful to change afterwards. `bordered` (§2.15) is deliberately *not* one of them - it is a single class on the root element, so it stays a writable accessor.
- **Headless-safe**: every element access is guarded, so a Pin without a `document` is still a fully functional spatial/trait entity.

### 2.2 Generic Trait Abstraction
- **Role**: All Pin functions and features are abstracted into reusable, composable Traits.
- **Contract**: `PinTrait` declares `name` and `capabilities` as subclass invariants (`fixed`); caller options may extend capabilities but never rename a trait. Lifecycle hooks: `onAttach`, `onDetach`, `onTick`, `onRender`, `onGlobalRender`, `onActivate`, `onDeactivate`, `onFocus`, `onUnfocus`, `onTransmit`, `onPointerDown/Move/Up`.
- **Core Trait Set**:
  - **`DisplayTrait`**: Dictates DOM rendering templates (`card`, `vector-pointer`, `media`, `raw`, `preserve`) from the Pin's Contents Map. `preserve` is the adoption template: build/update are both true no-ops, so a Pin created from a caller-supplied element (`session.adopt`/`session.hydrate`) keeps its authored markup untouched forever unless the caller later calls `setDisplayTrait` to something else. Each template builds its subtree once (`pin._display.bindings`) and thereafter mutates text nodes, attributes, and only those SVG slots whose inputs changed, so contents are escaped by the DOM; the `html` content key is the single, deliberate markup opt-in. `allowedKeys` optionally constrains the Contents schema.
    - **Supplying a custom display is `options.displayTrait`** (or `options.type`, which takes a registry name as well as an instance). Every non-utility Pin is born with exactly one display trait, and `initTraits` (`src/pins/pin-traits.js`) resolves that in one place: `type` if given, else `displayTrait`, else `new DisplayTrait({ displayType: content ? 'raw' : 'card' })`. Passing a display trait through `traits: [...]` instead **throws** - by then the default has already been attached under the name `display`, a Pin holds at most one trait per name, and `addTrait` refuses the duplicate rather than silently deciding which of the two draws the Pin.
    - After construction, the swap is `pin.setDisplayTrait(traitOrName, options)` - atomic, and it restores the previous display trait if the replacement fails to attach - or `pin.replaceTrait(traitOrName, options)`, which is the same detach-then-attach for a trait of any name. `replaceTrait` is also the escape hatch for a custom display arriving after the Pin exists: `pin.replaceTrait(new DisplayTrait({ name: 'display', build, update }))`.
  - **`FocussableTrait`**: Marks a Pin as a zoom target, carrying its own framing (`padding`, `maxZoom`) and optional `focusOnClick`. **Framing only** - the reticle is the session's `cursor-focus` cursor (§2.9), so colour, label, and the frustum toggle are properties of the cursor definition, not of every focussable Pin.
  - **`ScopeTrait`**: Treats a Pin as a nested container workspace hosting child Pins.
  - **`DraggableTrait`**: Implements pointer dragging, drag offsets, and `is-dragging` state.
  - **`SelectableTrait`**: Implements selection toggling, active outlines, and selection hooks.
  - **`ResizableTrait`**: Pointer-driven resizing from edge and corner handles - the structural twin of `DraggableTrait` over the Pin's *box* rather than its position (§2.15).
  - **`PhysicsTrait`**: Unpins the Pin's particle and applies harmonic drift as a `dt`-scaled force. Velocity damping is **not** here - it lives in `PinParticle.update()`, where friction is exponentiated by `dt` (`friction ** dt`) so the decay curve is frame-rate independent.
  - **`resizePin(pin, width, height)`**: Free helper applying a new box to a Pin - the DOM write, the particle write and the invalidation that a resize owes the renderer, in one call (§2.15).
  - **`rotatePin(pin, deltaDeg)`**: Free helper rotating a Pin's primary vector and mirroring the normalised angle into its Contents (the `vector-pointer` DisplayTrait draws the needle and gradient meter).
  - **`ConnectableTrait`**: Manages visual linkages / SVG bezier connectors to other Pins rendered into the global SVG layer.
  - **`TransmitterTrait`**: Programmable event dispatcher, signal broadcaster, telemetry router, and listener registry; optionally relays one hop along `ConnectableTrait` links with a `relayChain` that terminates mutual connections.

### 2.3 Trait Factory Registry
- **Role**: Singleton factory mapping a trait name to a **definition**: `{ name, ctor, defaults }`.
- **Responsibilities**:
  - `register(name, ctor, defaults)` - names are unique; re-registering an existing name throws rather than silently replacing a definition other code depends on. `unregister(name)` releases it, `clear()` restores the built-in set.
  - `create(name, options)` returns a **fresh instance** every call, shallow-merging caller options over the registered defaults (`capabilities` is the one additive key). Pins therefore never share mutable trait state.
  - Built-ins: `card`, `vector-pointer`, `media`, `raw`, `preserve`, `draggable`, `selectable`, `physics`, `connectable`, `focussable`, `scope`, `transmitter`, plus the cursor definitions (`cursor-focus`, `cursor-selected`, `cursor-activated`) contributed by `registerDefaults(provider)` - the hook for built-ins that live outside this module and are replayed by `clear()`.
  - The registry holds definitions only; the live instance index is `PinManager.traitIndex` / `capabilityIndex`, which is what `session.regraph(name, fn)` and the global SVG pass look through.

### 2.4 ConjugateRenderer Frame Contract
- **Role**: Single authority over DOM membership and per-frame work. Nothing else mounts, hides, or detaches a Pin's element while a renderer is attached.
- **Two sets, two meanings**: `activeSet` is *ownership* (which Pins this renderer is responsible for); `liveSet` is *participation* (which of them get per-frame work). A dormant Pin leaves `liveSet` but keeps its renderer, so it can still be invalidated and woken.
- **Three ordered phases per frame, never interleaving reads with writes**:
  1. **Structure flush** - dirty Pins are processed shallowest-first (so a parent's scope container exists before its child mounts). Each resolves through reload policy to `mounted` / `dormant` / `unmounted`.
  2. **Read phase** - every layout read of the frame (`offsetWidth` / `offsetHeight`, scope offsets) happens here. Dormant Pins are skipped: with no layout box, their last measured size stays authoritative.
  3. **Write phase** - content for dirty *and live* Pins, a three-float position diff across every live Pin (transform written only when the particle actually moved), the plane transform when `viewportVersion` moved, then the global SVG groups last, so every group sees the frame's final geometry.
- **Invalidation contract**: `invalidate(pin, 'content'|'structure')` (unknown kinds throw), `reconcile(pin)` for reload-state changes, `enqueueMeasure(pin)`, `bumpViewportVersion()`. A Pin with no renderer records its invalidations and replays them at attach time, and renders synchronously in the meantime.
- **Dirty sets**: `dirtyContent`, `dirtyStructure`, `measureQueue` persist across frames; `_frameDirty` is rebuilt each frame and is what the SVG pass consults - and because global bounds are cumulative over the scope chain, a moved ancestor marks its whole subtree dirty. A dirty Pin that is asleep keeps its flag and renders once, on the frame it wakes.

### 2.5 Reload Strategies & Activation Lifecycle
- **Role**: High-performance selective rendering and execution for complex pin trees. The policy is pure and side-effect free (`src/pins/reload.js`); the renderer applies it in its structure flush, and an unattached Pin applies the same decisions synchronously.
- **Strategies**:
  - `reload: 'active'` (default): mounted while awake; **unmounted** from the DOM when it (or its scope) sleeps. The Pin instance, traits, contents and particle state are retained and restored on remount.
  - `reload: 'persistent'`: stays mounted when asleep, hidden with `.is-dormant`, out of the render loop - no ticks, no content writes, no measurement, so its cached size and last transform stay authoritative.
  - `reload: 'lazy'`: absent from the DOM until first required (activation or focus), at which point `loadChildren(pin, context) -> Promise<PinSpec[]>` provisions its scope. Once provisioned it behaves like `persistent`; `unload()` destroys the scope and re-arms the provider.
  - An unknown strategy string throws: a typo must never silently downgrade a Pin to a different lifecycle.
- **Provider resolution & guarantees** (`LazyChildrenLoader`): per-Pin `loadChildren` first, then `pin.options.loadChildren`, then the session/manager-level provider, then an empty default. Single-flight (concurrent triggers share one promise), run-once until `unload()`, removal-race-safe (specs resolved after the Pin was removed are discarded), and failure-safe - a rejection transmits a bubbling `childrenerror` event and leaves the trigger re-armed. Resolved specs are created through `PinManager.createPin`, so registries, indices, and the renderer stay the single source of truth.
- **Lifecycle**: `activate()` / `deactivate()` enable level-of-detail (LOD) and viewport culling. Activation wakes the subtree except unrequired lazy children; deactivation cascades through the scope tree first, then settles the Pin's own element. Focus is itself an activation trigger.

### 2.6 Hierarchical Scoping, Focus & Root Promotion
- **Frustum Projection**: Four tapered spikes reaching from the corners of the focused Pin's **parent scope** - its real measured box, not the viewport, which is what every reticle used to claim as its parent - toward the matching corners of the Pin itself, drawn by the `cursor-focus` cursor in the overlay (§2.9). A Pin at the canvas root has no parent scope and so no frustum.
- **Focus Cursor**: One reticle for one focus, owned by the session's cursor Pin and reskinned by re-registering its definition - never configured per focussable Pin.
- **Focus Navigation Stack**: `focus(pin, {promote})`, `pushFocus(pin, {promote})`, `promoteToRoot(pin)`, `popFocus()`, `goForward()`, `focusParent()`, `unfocus()`. Framing defaults come from the target's own `FocussableTrait` (`padding`, `maxZoom`); caller options win over them.
- **Zooming into a Pin promotes it, by default.** `session.focus(pin)` *is* `promoteToRoot(pin)` since 0.4.0: the targeted Pin becomes the new parent view, its siblings leave the active set, and a breadcrumb is what leads back out - which is what "zoom into a pin" always meant here. `focus(pin, {promote: false})` is the plain camera move, still available and no longer the default; `FocussableTrait({promote: false})` opts a Pin's click-to-focus out of it. Re-focusing the Pin that is *already* the promoted root re-frames it and stacks nothing, so repeat activation cannot fill the history with entries that go nowhere.
- **Stack entries carry three things** - the focused Pin, the camera triple, and the render root - so one restore path puts all three back.
- **Back and forward are browser-shaped.** `popFocus()` pops the focus stack and pushes what it left onto `_forwardStack`; `goForward()` is its exact mirror, sharing one `restoreState` so the pair is symmetric rather than merely similar. Any *new* navigation invalidates the forward history - enforced in one place, `focusPin`, which every new navigation runs through and neither traversal does. `goForward()` with nothing ahead is a no-op, not a reset: it announces nothing and moves nothing.
- **Root promotion**: promoting a Pin narrows renderer participation to its subtree plus its **full ancestor chain**. Everything else demotes exactly as if it had gone inactive - `participating: false` is indistinguishable, policy-wise, from `active: false` - so promotion needs no bespoke DOM path. Promotion mid-drag cancels the gesture rather than stranding it against a detached element.
- **Breadcrumbs**: the promoted Pin's ancestor chain stays live and mounted, which is what makes the trail navigable rather than torn down and rebuilt. `pin.ancestors()` (nearest-first), `pin.breadcrumb()` (root-first, ending at the Pin), and `session.breadcrumb()` (`[]` at the canvas root). `pin.scopeTrait(name)` / `pin.deriveFromScope(name, key)` read the nearest ancestor's trait state - opt-in per call, never cached or inherited automatically.

### 2.7 Multi-Layer Global Trait Rendering
- **Role**: The engine inherits and orchestrates the traits of all pins across dedicated layers.
- **Layers**:
  - **Layer 1**: Canvas background and grid (`.cloudcanvas-host`).
  - **Layer 2**: Global SVG Vector Layer (`.cloudcanvas-svg-layer`: connectors and force vectors, drawn in *canvas* coordinates and carrying the same camera transform string as the plane - which is what makes a connector land on the Pins it joins at every zoom).
  - **Layer 3**: Pin DOM Plane (`.cloudcanvas-plane`: root pins and nested child pin scopes, plus the focus veil as its first child).
  - **Layer 4**: Focus Cursor & HUD Overlay (`.cloudcanvas-overlay-layer`) - the one **untransformed** layer, so cursors draw in screen space.
  - The four are built (or adopted, on a re-mount) by `src/engine/host.js`, and every z-index among them is a `--cc-z-*` token.
- **Persistent SVG groups**: each trait declaring the `global-render` capability owns one `<g data-trait="NAME">`, created once and rewritten only when its own inputs moved - a carrier Pin is dirty, a Pin the trait *draws to* is dirty (`collectRenderDependencies`), the trait's Pin set changed size, or a trait instance bumped its own `revision` counter (the layer sums those across the participating Pins). The counter is how a *trait-internal* mutation becomes visible: `connectTo()` between two Pins that were already carrying `connectable` moves no geometry and no count. An idle frame performs zero `innerHTML` assignments. Groups whose trait leaves the index are retired.
- **Scope wells are granted, not default** (`ScopeWellPass`, `src/engine/scope-well.js`). Every Pin owns a scope container, so an empty one must cost nothing: the resting state is `display: none`, and the box, dashed outline, gap and clipping arrive with `cc-populated` when a live child is actually inside, together with a `min-height` measured from the children's own offsets. The pass runs in the write phase and reads no layout; a rewritten well re-queues its parent for measurement, which is what carries a size change one level further up. A populated well **clips** (`--cc-scope-overflow`, `hidden` by default), so a child cannot spill over its parent's siblings.
- **Stacking is a property of a chain** (`src/engine/elevation.js`). An element cannot paint above its ancestor's stacking context, so focusing or dragging a Pin marks every scope along its parent chain (`cc-elevated` / `cc-dragging`); a focus additionally raises `.cloudcanvas-focus-veil`, the plane-level dimmer that separates the focused subtree from everything else and is disabled with `--cc-focus-veil: transparent`.
- **`cc-moving`** (`MotionHintSet`) grants `will-change: transform` on the frame a Pin's transform is rewritten and sweeps it ~30 frames after it stops: a compositor hint is a promise to keep a layer alive, so a canvas of stationary Pins is worth zero layers.
- **The camera is an opt-in input** (`trait.screenSpace === true`). The SVG layer carries the *same* transform string as the plane, so a trait drawing in canvas coordinates - every built-in one - is still anchored to its Pins after a pan or a zoom, and rewriting its group would re-parse every path in the document on every frame of a camera animation. Only a trait that projects to screen space itself declares `screenSpace = true` and is redrawn on a camera move. Screen-space *cursors* are a separate system with the same gate (§2.9); they live in the untransformed overlay and must reproject, which is exactly why they are not `global-render` traits.

### 2.8 Native Event Transmission
- **Role**: One event system, native end to end. `Pin extends EventTarget`; `PinEvent extends CustomEvent`.
- **Wire format** lives entirely in `detail`, so an event survives any `dispatchEvent()` round trip: `detail.payload` (aliased as `event.payload`) and `detail.source` (origin Pin, or the origin Event for a wrapped foreign event). `target` is never assigned by hand - the DOM owns it. `stopPropagation()` / `preventDefault()` are native; `cancelled` is a legacy alias for `defaultPrevented`.
- **Lifecycle signals** (`activate`, `deactivate`, `select`, `destroy`) are non-bubbling `PinEvent`s announced on the Pin they happened to; `activate` / `deactivate` are a pair, each fired once per real transition. `PinManager` subscribes on registration and re-broadcasts them through the `PinSignalBus` (`onSignal(handler)`), giving the session one subscription point for state that changes *inside* a Pin - no polling and no second route.
- **`pin.transmit(event, context)`** normalises anything transmittable: a string becomes a `PinEvent`; a foreign `Event` is *wrapped*, never mutated; a duck-typed `{ type }` object passes through untouched (and simply skips native dispatch). At every node on the walk, trait `onTransmit` hooks run first, then the node dispatches the event **on the Pin instance** - `Pin extends EventTarget`, so the subscriber is `pin.addEventListener(type, handler)`, *not* `pin.element.addEventListener(...)`. Bubbling up the scope chain stops on a non-bubbling, cancelled, or propagation-stopped event.
- **The walk is the Pin's `.parent` graph, not DOM ancestry.** `transmit` climbs `node.parent` (cycle-guarded by a visited set) and dispatches on each Pin object it reaches. That is the whole reason the system exists: it works for a dormant or never-mounted Pin, for an elementless utility Pin, and - with `TransmitterTrait({ forwardToConnections: true })` - across `ConnectableTrait` edges that are not tree-shaped at all. It is also the whole reason it is *not* a drop-in replacement for a DOM event: nothing on `pin.element` hears it, and no element between the two Pins is on the path.

#### Native DOM events vs. `transmit()`

For an ordinary, always-mounted UI subtree, a child Pin's element really is nested inside its parent Pin's scope container, so **native bubbling already works and should be the first thing a component author reaches for**:

```javascript
// Native: real DOM nesting does the bubbling. No CloudCanvas API involved.
childPin.element.dispatchEvent(new CustomEvent('cardpicked', {
  bubbles: true,
  detail: { id: childPin.id }
}));

parentPin.element.addEventListener('cardpicked', (event) => {
  console.log(event.detail.id);
});
```

Reach for `transmit()` / `PinEvent` when the signal has to survive detachment, reach a Pin with no element, or cross a non-tree edge:

```javascript
// Pin transport: dispatched on the Pin object, walking Pin.parent.
childPin.transmit(new PinEvent('cardpicked', {
  payload: { id: childPin.id },
  bubbles: true
}));

// Subscriber is the PIN, not its element - so it fires even while the
// subtree is dormant, unmounted, or the listener is a utility Pin.
parentPin.addEventListener('cardpicked', (event) => {
  console.log(event.payload.id);   // detail.payload, aliased
});
```

| | native DOM | `pin.transmit()` |
| :--- | :--- | :--- |
| Dispatch target | `pin.element` | the `Pin` instance |
| Path | DOM ancestry | `Pin.parent` chain (+ `ConnectableTrait` edges) |
| Works unmounted / dormant | no | yes |
| Works for elementless utility Pins | no | yes |
| Runs trait `onTransmit` hooks | no | yes |
| Payload | `event.detail` | `event.detail.payload`, aliased as `event.payload` |

### 2.9 Cursor System
> What a cursor *is* lives in `src/pins/cursor.js`; when the session builds one, how signals become targets, and where the redraw sits in the frame live in `src/engine/cursors.js`.

- A single global **null utility Pin** (`__cursor__`, `utility: true`) - no element, no display trait, no interaction - carries one trait per cursor state. Utility Pins are filtered out of every caller-facing query (`getAllPins`, root/active lists, spatial queries); the engine's own `allPins()` still sees them, because the cursor Pin has to be findable by id.
- Three independent cursors - `cursor-focus` (reusing the focus reticle and frustum primitives), `cursor-selected` (a retained `<rect>` ring), `cursor-activated` (a retained `<path>` of corner brackets) - each own a `target` Pin and a persistent `<g data-cursor="NAME">` inside a shared `<svg class="cloudcanvas-cursor-layer">` in the overlay. Three different Pins can be focused, selected, and activated at once.
- **Shape**: `CursorTrait extends PinTrait` owns the target, the group, and the write gate; every cursor is a subclass implementing `draw(group, screenBounds, context)` and nothing else (`CursorFocusTrait`, `CursorSelectedTrait`, `CursorActivatedTrait`). All three declare the `cursor` capability, whatever class implements them.
- The overlay is the only untransformed layer, so cursors draw in **screen space**: the target's canvas bounds are projected through the viewport once per change. A cursor redraws only when its target changed, the camera moved, or its target's own geometry moved - the same gate the per-trait SVG groups use, and the reason an idle frame writes nothing.
- **Visibility gate**: a cursor draws only on a target that is *visible* - awake (`active`), still in the document, and inside the promoted render root (`context.participates`). A target that fails any of the three is treated as no target at all: the group is hidden and stops re-projecting. Hiding is not releasing - `trait.target` is kept, so waking the Pin, remounting it, or popping back to a render root that includes it brings the cursor straight back.
- Cursors are registry **definitions**, installed through `traitRegistry.registerDefaults(registerCursorTraits)`: they are built-ins that live outside the registry module, so `clear()` brings them back. Re-registering `cursor-focus` (or either sibling) with another constructor - or the same one under different defaults - reskins it wholesale, and no focussable Pin is touched. On a live session `session.remountCursors()` rebuilds the cursor Pin from the registry, carrying its current targets over, which is what makes a reskin visible without a re-mount.
- **The reticle's caption is not the reticle's colour.** The stroke is a marker - it is read as a shape against whatever it is drawn over, and `--cc-cursor-focus` is the right marker. The caption is *text*, and text has a contrast floor the focus red cannot clear (2.29:1 on the default canvas). It is painted from `--cc-cursor-label`, whose fallback chain runs through `--cc-text` before its own literal, so the caption is the canvas's own body colour by default and a theme carries it without naming the token. `CursorFocusTrait({ labelColor })` and `createFocusCursorSVG(bounds, { labelColor })` are the per-cursor and per-call knobs; the element is `.cloudcanvas-focus-cursor-label`, which is how the browser suite measures it on the zero-CSS fixture in both themes.
- **Single writer**: focus targets are written by `navigation.js`; `select`, `activate`, `deactivate` and `destroy` arrive as Pin lifecycle signals through the `PinSignalBus` (`PinManager.onSignal`) and are turned into targets in exactly one place (`handlePinSignal`) - a destroyed Pin releases every cursor holding it, a deselected one releases `cursor-selected`, and a deactivated one releases `cursor-activated`, because activation has genuinely ended rather than merely gone off screen. There is no polling and no second route. The cursor pass runs after the renderer's frame, so it sees final geometry - retiring the `FocussableTrait.onGlobalRender` focus branch of the SVG group layer.

### 2.10 Pointer & Wheel Contract
> Routing in `src/engine/pointer.js`; the maths it routes on is pure and lives in `src/engine/wheel.js`.

- **One rule**: a pointer event that lands on a Pin is delegated to that Pin's traits and never interpreted by the engine; a pointer event that lands on nothing is a camera gesture. No trait registers a DOM listener of its own. The session owns the gesture *state* (`activeDragPin`, `isPanning`, `lastPointer`, `activePointers`, `pinch`); the module owns the transitions.
- **Admission**: `isPrimary && button === 0`, with one exception - the second finger of a touch pinch is non-primary by definition and is admitted only while exactly one gesture pointer is already down, never from idle.
- **Pinch**: two live pointers cancel any drag and any pan. Each step scales by the ratio of separations **about the previous midpoint** (the only focal point that keeps both fingers glued to the content) and then translates by the midpoint delta. Lifting back to one pointer re-seeds the pan from the survivor, so the gesture degrades without a jump. The invariants (`pinchStateFrom`) are pure.
- **Capture is best-effort and deliberately declined** for a gesture starting on a platform control (`button`, `a[href]`, `input`, `select`, `textarea`, `label`, `contenteditable`) or inside selectable text: capture retargets `pointerup`, the compatibility `mouseup`, and the `click` derived from them, which kills both the control and the browser's own text-selection drag. The window listeners are the delivery path regardless.
- **Two exemptions and a threshold, all of them `DraggableTrait`'s.** The control list above is one exported constant (`CONTROL_SELECTOR` / `isControlTarget`, `src/pins/pin-element.js`) read by both layers, so the router declining to capture and the trait declining to drag can never disagree; the text-region flag (`_ccTextRegion`) is the second exemption, drawn by `isTextRegionTarget` in the same module. On top of both, translation begins only once the pointer has travelled more than `DRAG_THRESHOLD_PX` (3px) - a click carries a pixel or two of wobble, and a card that shifts under every click is a card that cannot be clicked. The threshold sits deliberately under `FocussableTrait`'s `CLICK_TRAVEL_PX` (5px) so both guards agree on what a click is, and the drag offset is measured at the *press*, so the travel spent crossing the threshold is carried rather than swallowed.
- **Wheel routing**, in order, on clamped pixel intent: `ctrl`/`meta` -> zoom at the pointer with the pinch gain; a discrete-looking notch -> zoom at the pointer with the wheel gain; anything else -> **pan** `(-dx, -dy)`. `deltaY === 0` never zooms. `preventDefault()` is unconditional and the listener is registered `passive: false`.
- **Constants** (all exported, all tunable): `LINE_HEIGHT_PX` 16, `PAGE_HEIGHT_FALLBACK_PX` 800, `MAX_WHEEL_DELTA_PX` 160, `PINCH_ZOOM_K` 0.01, `WHEEL_ZOOM_K` 0.0015 (~1.2x per 120px notch, and `exp` is its own exact inverse), `DISCRETE_WHEEL_MIN_PX` 40. The classification is stateless - no accumulator, no timer, no per-device memory - and the clamp is what makes a misclassification a wobble rather than a teleport.
- **`contextmenu`** has three outcomes, in order: mid-gesture it is swallowed and the gesture cancelled rather than left running under an open menu; otherwise the click is resolved to a context (`{pin, x, y}`, `pin` null on bare canvas) and offered to the menu registry (§2.16); and if no command applies, the event is left completely alone so the platform's own menu opens.

### 2.11 Keyboard Navigation
> `src/engine/keyboard.js`. Bound by the session at mount, removed by `destroy()`; nothing survives it.

- **Two stages, one tab stop.** The host is `tabindex="0"` (set only if the author left it unset) and every Pin is `tabindex="-1"`, so Tab reaches the canvas and stops - a keyboard user never walks through hundreds of cards to get past it. `Enter` descends into the Pins, `Escape` returns to the host: `Escape` always means "one level out" and focus is never trapped.
- **Roving is reading order** - top-to-bottom, then left-to-right, over participating (`renderer.participates`) and awake Pins, with ids breaking exact ties so the sort is total. 2D spatial navigation was rejected: it is ambiguous the moment two Pins overlap or a row is ragged, and its failure mode is a Pin that can never be reached. The order is recomputed on entry, and again whenever the focused Pin is not in it.

| Key | Host focused | Pin focused |
| --- | --- | --- |
| `ArrowLeft` / `ArrowRight` | pan -/+ 40px on x (x4 with Shift) | step back / forward in reading order |
| `ArrowUp` / `ArrowDown` | pan -/+ 40px on y (x4 with Shift) | step back / forward in reading order |
| `+` `=` / `-` `_` | zoom 1.2x / 1÷1.2x about the host centre | - |
| `0` | reset the view | - |
| `Enter` | enter pin navigation (focused Pin, else first) | `session.focus(pin)` - zooms in, promoting it (§2.6) |
| `Space` | - | run the Pin's `onAction` traits |
| `Escape` | `popFocus()`, else `unfocus()` | back to the host |
| `Home` | `unfocus()` | - |

- **Enter enters, Space acts.** Enter is navigation - on a Pin it is `session.focus(pin)`, which descends one scope (promoting it), and `Escape` at the host stage walks the same steps back out; Space is activation - it walks the focused Pin's traits calling `onAction(pin, event, session)` where one is defined, and the first truthy return consumes the press (`preventDefault` + `stopPropagation`). A Pin whose traits all decline leaves Space to the page rather than swallowing it, and a native control inside a Pin keeps its own Space through the same key-owner rule below.
- Arrow panning is **content-following** (`ArrowRight` pushes content right), the same convention the wheel's two-axis scroll uses. Zoom has no pointer to anchor on, so it uses the host centre - the only choice that keeps what the user is looking at on screen.
- Only *handled* keys are defaulted away, and nothing is taken from an editable target or a native control (`INPUT`, `TEXTAREA`, `SELECT`, `OPTION`, `BUTTON`, `contenteditable`) - a canvas hosting real controls has to stay usable.
- **`ensureVisible(session, pin)`**: the minimum scale-preserving pan that puts a Pin plus a 24px margin inside the host box, over 200ms. Roving is not framing - `focus()` is what zooms - and a Pin larger than the host has its top-left corner aligned, which is where its title is. Reduced motion is inherited, not re-implemented: `animateTo` is the choke point.
- The table itself is exported as `KEY_BINDINGS`, as data, keyed by `KeyboardEvent.key`.

### 2.12 Accessibility Contract
> Static identity and the live region in `src/engine/announcer.js`; the pin half in `pin-element.js` / `pin-render.js`.

- **Host**: `role="application"` + `aria-roledescription="canvas"` + `aria-label` (`options.label`, default "Interactive canvas"). `role="application"` hands every key to the page, so it may only ship on a host that gives every key back - §2.11 is that promise, and the two must never be separated.
- **Pins**: `role="group"` + `aria-roledescription="pin"` written once at setup, and `aria-label` funnelled from the `title` content through the render path (`writeAriaLabel`), change-gated against a value cached on the Pin so the idle-zero-write invariant holds. A Pin with no title is named by its id: a `group` with no accessible name announces as nothing.
- **Author values always win, in both directions.** Every one of those attributes is written only if absent, including `tabindex` - and *which ones were actually written* is recorded on the session, so `destroy()` reverses exactly those and leaves an author's own `role`, name, `tabindex` or `cloudcanvas-host` class in place. A bare `<div>` mounted and destroyed comes back with zero attributes and zero children; the reversal is split across the three modules that made the additions (`unbindKeyboard` -> `tabindex`, `removeHostAria` -> role and name, `unmountLayers` -> the layers and the host class, including the empty `class=""` an unconditional `classList.remove` would leave behind).
- **Decorative layers are hidden**: the SVG layer, the focus veil and the cursor overlay are `aria-hidden="true"` - the first and last are projections of Pins already in the tree and announcing them would double every Pin, and the veil is a dimming surface with no content at all.
- **Live region**: one polite `role="status" aria-atomic="true"` div per session, visually hidden by class *and* by an inline copy of the same rules (the stylesheet is optional and a consumer reset can flatten a class; a region that is `display: none` is not read at all). `announce()` drops empty messages and toggles a trailing no-break space on repeats, because a live region announces *changes* and two identically-titled Pins would otherwise be silent the second time. Announced: every focus transition (through the session's wrappers, so pointer, keyboard and API routes all pass one point), provider results, and provider failures.
- **Reduced motion**: `prefersReducedMotion()` caches one `matchMedia` query and tracks changes; when it matches, `animateTo` jumps and fires `onComplete` synchronously. The CSS half is a `@media (prefers-reduced-motion: reduce)` block covering pins, the focus veil, and the inline transitions the SVG generators carry.
- **Contrast by construction**: `relativeLuminance` / `contrastTextFor` / `compositeOver` (`graphics/primitives/contrast.js`, exported from the package root) are WCAG 2.x throughout. Hex only - a `var()` read has no value until the cascade runs, and a contrast decision made on a guess is worse than none, so unknown colours return `NaN` and every caller leaves them alone.
- **Selectable text**: `selectableText: true` gives a Pin `is-selectable-text`; the content node gets `user-select: text` and a text cursor, a `pointerdown` inside it is flagged so `DraggableTrait` stands down and the pointer stream is not captured, and the header row is held back as the drag handle (`user-select: none`, `cursor: grab`). A nested child Pin is reached through the scope container, never the parent's content node, so it stays draggable.
- **Real controls stay operable**: a press on a `button`, link, form control or `contenteditable` inside a Pin neither captures the pointer stream nor starts a drag (§2.10), so the click the platform computes from it arrives at the control - a canvas hosting real UI has to stay a canvas hosting real UI.

### 2.13 Design System & Theming
> `src/graphics/styles-css.js` (the sheet), `styles.js` (injection), `theme.js` (the token API).

- **The dark theme is the fallback chain.** There is no `:root` block: every themable value in the sheet is a `var(--cc-*, <dark default>)` read, so a host that defines nothing still looks designed and a host that defines one token changes exactly one thing. `tests/unit/styles.test.js` enforces this as a permanent invariant, along with "every class a template emits has a rule" and "no template ships an inline style".
- **Token groups**: foundations - `--cc-font`, `--cc-type-*`, `--cc-space-*`, `--cc-radius-*`, `--cc-shadow-*`, `--cc-z-*`, `--cc-control-min*`; parts - `--cc-bg`, `--cc-grid-*`, `--cc-text*`, `--cc-accent`, `--cc-focus*`, `--cc-card-*`, `--cc-scope-*` (including `--cc-scope-overflow`), `--cc-badge-*`, `--cc-btn-*`, `--cc-meter-*`, `--cc-connector`, `--cc-cursor-*`.
- **`applyTheme(host, vars)`** writes inline custom properties on the host element - not a stylesheet swap. That outranks any author rule without `!important`, scopes to one session on a shared page, and is reversible in a single call. A `null` value removes one token; a `null` map removes them all, which is the same operation as returning to the dark default. Keys outside the `--cc-` prefix are ignored: a theme may not reach past the framework's own surface. `LIGHT_THEME` is the frozen reference override set, and holds only tokens whose dark fallback is actually wrong on a light surface - geometry is theme-independent.
- **The one thing a token cannot reach** is a value computed per Pin and written inline. Badge text is the case: it is chosen per tint against an assumed surface, so it is emitted as the *fallback* of `--cc-badge-text-override` and a theme sets that token to take the decision back (§2.12, CHANGELOG 24).
- **Injection**: `injectCanvasStyles()` writes the base sheet exactly once per document (re-writing a live `<style>` invalidates every rule the browser has already matched); `injectSessionStyles(css)` returns a removable `<style data-cc-session>` element, which is how one session's CSS is torn down without touching another's.
  - **Scoping caveat**: `injectSessionStyles` is *removable*, not *scoped*. The element goes in `document.head` and its rules are global for as long as it is there, exactly like any other `<style>` - a `.cloudcanvas-pin-title { color: red }` passed as one session's `customCSS` repaints every session on the page. There is no way around that from inside the framework: CSS has no host-scoping primitive short of a shadow root, and the canvas deliberately renders into the page's own tree so consumer styles, fonts and dev tools all keep working. **Consumers scope their own selectors** - prefix each one with a host selector they control (`#board-a .cloudcanvas-pin-title { ... }`), which is what the per-session token surface (`applyTheme`, §2.13) already does for values. What `injectSessionStyles` guarantees is the *teardown*: `destroy()` removes exactly that element and nothing another session depends on.

### 2.14 Placement
> `src/engine/placement.js`, surfaced as `session.place(options)`.

- **`place({ width = 200, height = 120, near, anchor, margin = 24 })` -> a canvas-space top-left.** The anchor is, in order: an explicit `anchor`, the centre of a `near` Pin, or the screen centre of the current viewport - box-centred in all three cases.
- **Ring search**: the anchored box itself is tried first, then `k = 1..12`, radius `k * (max(w, h) * 0.75 + margin)`, `8 + 4k` samples per ring, walked in a fixed order. A candidate is free when the padded box hits no Pin (`session.queryBox`, utility Pins filtered out). If every ring is exhausted the last candidate is returned - a placement always succeeds.
- **Deterministic**: the same canvas returns the same answer, which is what makes "nine spawns never overlap" a test rather than a hope.

### 2.15 Resizing & the Border Toggle
> `src/pins/traits/resizable.js` (the trait), `src/pins/pin-element.js` (the border class), `styles-css.js` (both).

- **`bordered` is finer-grained than `chrome`, and independent of it.** `chrome: false` takes the whole card away - surface, padding, radius, shadow, border - for a component that draws its own. `bordered: false` leaves every one of those standing and withholds only the border. It is *not* a construction-time invariant like `utility` and `selectableText`: the state is one class (`is-borderless`) on the root element, so `pin.bordered` is a real get/set pair alongside `selected`/`dragging`/`pinned`, writable at any time. The flag lives on the Pin and the class mirrors it, so a headless Pin still remembers what it was asked for.
- **The stylesheet's half is `border-color: transparent`, not `border: none`.** `box-sizing: border-box` only makes a *specified* width include its border; a card that sizes itself to its content has none, so removing the border shrinks it by 2px in each axis and moves the content box of an explicitly-sized one by the same amount. The toggle must be a repaint, never a reflow. The rule is stated twice - plain and `:hover` - because `.cloudcanvas-pin:hover` sets a border colour at equal specificity and source order must not decide it.
- **`ResizableTrait` is opt-in, and holding it *is* the resize toggle.** `pin.addTrait('resizable', options)` grants it; `pin.removeTrait('resizable')` ends any live gesture (as a cancellation), releases the selection listener, and takes every handle element back out of the DOM.
- **Handles are a table, not eight branches.** `RESIZE_DIRECTIONS` (`n s e w ne nw se sw`) drives handle creation, the arithmetic, and the cursor the stylesheet picks; each direction is a unit step per axis, where `-1` means the *near* edge follows the pointer, so the extent grows against the delta and the origin moves to hold the far edge still - including while the box is clamped against its own minimum. Options: `directions` (an unknown one throws), `minWidth`/`minHeight` (default 40 x 24), `maxWidth`/`maxHeight` (unbounded, and never below the matching floor), `alwaysVisibleHandles`.
- **Handles are chrome, not content.** They are appended to the Pin's *root* element - not the content node, which display traits rebuild, and not the scope container, which holds child Pins and is measured as a well. Each carries `data-cc-control`, which is the single declaration that makes the pointer router decline the deferred capture and `DraggableTrait` stand down (§2.10); the consequence is that a resize is delivered by the window listeners rather than a captured stream, which is the same path that carries every gesture leaving the host box. Each also carries `data-cc-resize-handle="<direction>"`, and the trait identity-checks that attribute against its own map, so a *child* Pin's handle - a descendant of the parent's element too - never resizes the parent.
- **Visibility follows selection**, through the `select` signal rather than a poll: handles show only while `pin.selected`, unless `alwaysVisibleHandles: true`. A Pin built with `selectable: false` has no selection to follow and needs that option. The mechanism is the `hidden` property, not a class, so it still holds on a page that never loaded the framework stylesheet.
- **The gesture is `DraggableTrait`'s, over a different quantity**: the same `DRAG_THRESHOLD_PX` (imported, never restated), the same one-way gate, the same "announce at the threshold, not at the press" discipline, and the same cancellation convention - a missing event on `onPointerUp`. `resize:start` carries `{width, height, direction}`, the box being left from; `resize:end` carries `{width, height, cancelled}`. Both are in `PIN_SIGNAL_TYPES`, so `PinSignalBus` relays them like every other Pin signal. Deltas are projected through `screenToCanvas` at both ends, so a resize is correct at every zoom and survives a pan mid-gesture.
- **`resizePin(pin, width, height)` is the programmatic route**, a free function for the same reason `rotatePin` is one: resizing is an operation *on* a Pin carrying no per-Pin state, and a caller should not have to attach an interaction trait to do it.
- **The DOM is the size authority, and that is what makes a resize visible.** The renderer never *writes* a Pin's box - its read phase *reads* `offsetWidth`/`offsetHeight` into the particle (§2.4), so `particle.setSize` alone changes nothing on screen and is overwritten by the next measurement. `resizePin(pin, width, height)` therefore does three things: writes the element's inline `width`/`height` (with `max-width: none`, so the card's readable-measure clamp cannot cap a size the user just dragged out), writes the particle so canvas geometry is right for the gesture's next move and for layout-less environments, then `invalidate('content')` - which is what queues the next read phase *and* puts the Pin in the frame's dirty set, so connectors anchored to its centre and the scope well it sits in both follow it. A geometry change the renderer is not told about is a Pin that resizes with a stale connector hanging off it.

### 2.16 The Context Menu
> `src/engine/context-menu.js` (registry + overlay), `src/engine/pointer.js` (the door), `styles-css.js` (`.cloudcanvas-context-menu*`). The nesting half is used as its primary interface by §2.21.

- **A registry, exactly like traits are.** `registerMenuItem({id, label, when, action, group, parent})` / `unregisterMenuItem(id)`, over a `MenuRegistry` singleton whose `clear()` restores the built-ins. Ids are unique - re-registering one throws rather than displacing a command something else put there - and registration order is render order. A third-party command is a first-class one: the built-ins are registered through the same call.
- **`when(session, context) -> boolean` is asked per opening**, never cached, with `context = {pin, x, y}` and `pin` null on bare canvas. `action(session, context)` runs on click, and the menu closes after it - in that order, so an action may open something of its own.
- **Built-ins**: `nav-back` ("Back", while the focus stack has anything on it -> `popFocus()`), `nav-forward` ("Forward", while the forward stack does -> `goForward()`), and the Pin-scoped pair `bring-to-front` / `send-to-back`.
- **Z-order is DOM order.** `bringToFront(pin)` / `sendToBack(pin)` move the Pin's element among its siblings and nothing else: paint order among equals *is* document order, so there is no z-index bookkeeping to keep in step and no second ordering model to disagree with the tree. Send-to-back stops in front of the focus veil, which is the plane's deliberate first child. The structure flush only appends a Pin whose parent changed, so a reorder survives every later frame. Elevation (§2.10, `cc-elevated`/`cc-dragging`) is the orthogonal axis and still outranks it.
- **Nesting is derived from `parent`, never flagged.** A command may name another as its `parent` (`''`, the default, is the top level). Any command that at least one other names *becomes* a submenu trigger: it renders with a caret (`MENU_ITEM_SUBMENU_CLASS`, `aria-haspopup`/`aria-expanded`) and opens a flyout of its children instead of running. There is no `submenu: true` to keep in step with the children, and because a child of a flyout may itself be a third command's parent, the same mechanism composes to **any depth** with no per-level code. `MenuRegistry` exposes `hasChildren(id)` and `childrenOf(id)` for it.
- **Two authoring mistakes throw at registration**, the same contract the duplicate-id throw already set: a `parent` that is **not yet registered** (so the graph stays an acyclic forest and render order stays top-down), and a parent that **already carries an `action`** (a command cannot be both a trigger and a command). `action` is therefore optional - but only for a trigger; a leaf without one is invisible.
- **An empty category never renders.** Visibility recurses: a trigger shows when its own `when()` passes *and* at least one descendant would itself show, so a category whose every child is gated out never appears as a caret opening onto nothing. The recursion is what carries that judgement arbitrarily deep for free.
- **The menu is one element in the overlay layer**, built by `mount()` and removed by `destroy()` - the veil/cursor pattern - `hidden` between openings and rebuilt per click. It is positioned from the click's host-relative coordinates because the overlay is the one layer that draws in screen space, and it takes its pointer events back from an otherwise inert layer. **Flyouts are transient** (`MENU_FLYOUT_CLASS`) - created on open, removed on close - because there may be zero or many and their contents are per-opening; only one branch is open per level, so opening a trigger drops a sibling's flyout while leaving every ancestor in place.
- **One placement helper serves the root and every flyout.** The root anchors at the click, a flyout at its trigger's right edge, and from there the clamp back inside the host box is identical - which is the point of factoring it. It is unhidden *before* it is measured, because a `display:none` box measures as zeros and the clamp would silently no-op. *Known limitation*: a flyout with no room to its right is clamped rather than **flipped** to the trigger's left, so near the host's right edge the panels stack on one another and the trigger that opened one is covered by it. Every item in the innermost panel stays clickable; the ancestor trigger does not. Flipping changes this helper's contract (a point anchor should clamp, a box anchor should flip), so it is recorded rather than made silently.
- **Every item is a real `<button>`** inside `role="menu"`, so keyboard operation is the platform's rather than ours; the first item takes focus on open, and closing hands focus back to the host - asked *before* the buttons are torn out, because removing the focused element drops focus to the body. It closes on an outside `pointerdown`, on `Escape`, and on running a command. With a flyout open, **Escape steps back one level** rather than closing everything - the app-menu convention - Up/Down rove within the focused panel and wrap, Right opens the focused trigger's flyout and steps into it, and Left closes the flyout focus is in and returns to its trigger.
- **The native menu is a real outcome, not a dead branch.** Suppression is earned: if no command's `when()` passes, the event is left completely alone and the platform's menu - reload, inspect, spellcheck - opens as it always did. Core code throughout: plain DOM and `--cc-*` tokens, and no import from `lib/`.

### 2.17 The Sandbox Builder Example
> `examples/website-sandbox*.js`, the product site's fourth tab. Not part of the framework - an application built on it, kept here because what it needed and what it had to supply itself is the sharpest available statement of where the public surface ends.

- **What it is.** A site builder: the sixteen `lib/` base widgets plus a Container, inserted from the canvas's own right-click menu (§2.21), an infinite canvas, a quick-panel and a full editor modal for one Pin (§2.21), user-defined Pin types (§2.22), and named profiles that auto-save to `localStorage` and export as a standalone static site. Fifteen files - `website-sandbox.js` (session and wiring), `-chrome.js` (markup and the dialog shell), `-widgets.js` (the catalogue by category, the two placement calls, and the flat insertable set), `-menu.js` (the `+ New ▸ Category ▸ Item` insert tree and the per-Pin menu items), `-quicksearch.js` (Shift+A: the same set as a searchable list), `-inspector.js` (the quick-panel), `-editor.js` (the editor modal), `-editor-content.js` (its content section), `-schema.js` (what each widget's contents are made of), `-creator.js` (the "+ New Type" modal), `-fields.js` (the form atoms the panels share), `-profiles.js` (which canvas is being edited), `-frame.js` (windowed mode's device-sized page frame, §2.24), `-layout.js` (the one place a container's layout mode is read or written, §2.23), `.css.js` + `-frame.css.js` (the stylesheet, in core `--cc-*` tokens, injected as one sheet).
- **Public surface only, and specifically these entry points**: `pin.setPosition(x, y)` for moving (§2.1 - `pin.x/y/z` are read-only getters onto the particle, because the three coordinates are written together), `resizePin(pin, w, h)` for sizing (§2.15), `pin.setContent(key, value)` for contents, `pin.bordered` and `pin.chrome` for the border and the card (§2.18), `pin.addTrait` / `pin.removeTrait` / `pin.replaceTrait` for behaviour, `pin.reload` for the lifecycle (§2.5), `reparentPin(pin, null)` for Detach (§2.19), `registerMenuItem` for its own commands (§2.16), `session.createPin` for a placement, `session.removePin(id)` for deletion, `session.place({within})` for a free spot inside a Container, `session.pinManager.onSignal` for every state change it follows, and `session.viewport.screenToCanvas` for a click point.
- **Nothing polls.** The quick-panel follows the `select` signal, not the click that caused it; a live drag or resize has only a start and an end signal (§2.15), so between them the panels follow the pointer and detach on the end rather than reading geometry every frame.
- **The context menu needs no call.** `session.mount()` already runs `mountContextMenu` (§2.16), so Back / Forward / Bring to front / Send to back work on any mounted session.
- **The one thing the core does not supply: selection is not wired to the pointer.** `SelectableTrait` owns the state, the class and the signal, but no layer in `src/` routes a click into it. That is deliberate rather than missing - what a click on a Pin *means* (replace, add, toggle, rubber-band, nothing) is an application decision - and it is worth stating here because every consumer building an editor will look for it. The builder's answer is thirty lines: a `pointerdown` on the host, `closest('.cloudcanvas-pin')`, single selection on the primary button.
- **Widgets are placed with `chrome: true`, against `lib/`'s own default.** A `lib/` widget is chromeless because a widget is not a card, which for a Button means the Pin *is* a `<button>` - and `DraggableTrait` stands down on a real control on purpose (§2.10), so a chromeless Button has no *self-evident* draggable surface and no painted border for `bordered` to withhold. The card's padding is both. Since §2.18 the grab handle covers the drag half for a chromeless control directly, so this is now the builder's preference (a card is what a site-builder widget should look like) rather than the only workable choice.

### 2.18 Chrome, and the Chromeless Grab Handle
> `src/pins/pin-element.js` (`setChrome`/`syncChrome`, `CARD_CLASS`), `src/pins/traits/interaction.js` (the handle), `styles-css.js` (both halves).

- **`chrome` is one class on the root, and therefore a live accessor.** `pin.chrome` is a real get/set pair alongside `bordered`, `selected` and `dragging`. It is the presence of `cloudcanvas-primitive-card`, and nothing else - there is no wrapping card *element*. The Pin holds the flag and the class list holds the paint, so a headless Pin still remembers what it was asked for.
- **Content is preserved by construction, not by rebuilding.** The fixed `.content + .scope` two-child structure is built exactly once and identically whether or not the card is worn (§2.1), so a chrome toggle is a *class-level* change that cannot disturb the content node. `contentElement` and every node inside it survive by identity across any number of toggles. This is worth stating plainly because "remove the card" sounds structural and is not: nothing is torn down, and no display trait re-renders to restore anything.
- **It calls `invalidate('content')` where `bordered` does not, and that is the one real difference between them.** `bordered` is `border-color: transparent` - a repaint that moves nothing (§2.15). Chrome is real padding, a real border *width* and a shadow, so dropping or restoring it **changes the layout box**. The particle, any connector anchored to this Pin's centre, and the scope well it sits in all read that box, so a live change owes the renderer the same debt `resizePin` pays (§2.15): a geometry change the renderer is not told about is a Pin whose connectors and containing well are stale. The write is gated on an actual change with an element present, so setting the value already in force costs nothing.
- **At setup the class list is the authority; after setup the flag is.** `rootClassName` suppresses the card for three separate reasons - `chrome: false`, a caller's own `className`, and an adopted element that never passed through the builder at all - so at setup `syncChrome` *reads the flag back off the element* rather than writing it on. Only `setChrome` writes the class afterwards. A single authority in each phase, and no way for an adopted element to disagree with the flag describing it.
- **The grab handle exists for one situation, and is gated on exactly that situation.** `chrome: false` plus a content surface that is a real control - which is what a `lib/` widget is - leaves a Pin with nothing draggable: its whole face is a `<button>`, and `DraggableTrait` refuses a press on a control by design (§2.10). The handle is the drag surface put back. The gate is both halves: a chromed Pin is draggable by its padding and header row already, and a chromeless *non*-control (a divider, a bare adopted section) is draggable by its whole face. Neither builds one, so the ordinary canvas pays a single flag test per render. The control is read as the content node's **first element child**, which is where every `lib/` widget builds it - looking inside the content node only, so the framework's own root children (resize handles, this handle) can never be mistaken for it.
- **Wiring is `ResizableTrait`'s, deliberately, with one inversion.** A direct child of the Pin's **root** - not the content node a display trait rebuilds, and not the scope container that is measured as a well - so it rides the transform and survives both a content re-render and a reparent (§2.19). Visibility is the `hidden` property driven off the one `select` signal rather than a poll, so it still works on a page that never loaded the framework stylesheet. Existence is reconciled, not merely toggled: a Pin that no longer needs one has it removed from the DOM outright, matching how `removeTrait` disposes of resize handles. The inversion: it carries **no** `data-cc-control`, which is the whole point - a resize handle marks itself a control so the drag stands down on it, and this one must not, because initiating a drag is its entire job.
- **The reconcile runs on `onAttach` and on every `onRender`.** `onRender` is how a *live* `chrome` toggle arrives: the setter ends in `invalidate('content')`, so the render that follows adds or removes the handle to match. `onAttach` is what makes a trait added to an already-chromeless, already-selected Pin show its handle immediately rather than on the next unrelated render.

### 2.19 Reparenting: Nest and Detach
> `src/pins/reparent.js` (the primitive), `src/engine/hit-test.js` (the drop target), `src/pins/traits/interaction.js` (the gesture), `src/pins/pin-element.js` (`scopeOriginOf`).

- **One primitive, two directions.** `reparentPin(pin, newParent, position)` nests under `newParent` or - with `null` - promotes back out to the canvas root. Nest and detach are the *same* operation with the source and target roles reversed, so there is one function and no second code path to keep in step. A free function taking the Pin first, for the reason `resizePin` and `rotatePin` are free functions: it is an operation *on* a Pin carrying no per-Pin state to compose.
- **Never a rebuild.** The Pin instance survives untouched - `traits`, particle, selection, drag state, element, and every listener on it - and exactly two things change: which scope holds it, and where inside that scope it sits. Nothing is serialized and re-created, which is what makes a reparent safe mid-gesture.
- **Membership is reused, not reimplemented.** `addChild`/`removeChild` (§2.6) already relink the graph, move the element between scope wells, re-attach the renderer and wake the subtree - and `addChild` already detaches from the current parent first. What they do not do is convert coordinates, and that conversion is the entire content of this module.
- **The coordinate conversion is `scopeOriginOf`, and it is the inverse of `getGlobalBounds`.** A child is laid out inside its parent's scope container, so its canvas position is its own local position plus the parent's global top-left plus the parent's cached scope-container offset. `scopeOriginOf(parent)` is exactly that sum - the point a direct child's local `(0, 0)` lands at - so a canvas-space drop point becomes parent-local by subtraction. It is `globalBoundsOf`'s per-ancestor walk stopped one level up, which is why the two live in the same module and are read together. `position` is optional: with none, the Pin's current global corner is used, so a reparent with no position keeps it exactly where it is.
- **The cycle guard is a real guard, not an assertion.** A Pin can never become a child of its own descendant; the check walks `ancestors()` and *rejects the move* (returning `null`) rather than corrupting the tree. Self-parenting and the already-at-root no-op are rejected the same way.
- **The parent a Pin leaves is explicitly recomputed.** A departed child leaves no dirt of its own behind, so the vacated well would stay sized, outlined and `cc-populated` for a child that is gone. `removeChild` does not touch it - a *destroyed* child's well is handled by the renderer's `forget` - so a *live* reparent has to, in whichever mode the Pin is in: through the renderer's own well pass when one is attached (the same call `forget` makes), synchronously off the element otherwise. The new parent needs no equivalent nudge, because the moved Pin is dirty this frame and that is already what marks the parent holding it.
- **`droppablePinAt(session, event, {ignore})` is deepest-first, and that is the whole contract.** A nested Pin's element sits *inside* its parent's scope well, so the innermost Pin at a point is the topmost element in the paint stack there; `document.elementsFromPoint` returns that stack in that order, so the first resolvable Pin in it is the correct drop target. Resolution is the one hook every layer already uses - `.cloudcanvas-pin[data-pin-id]`, the same one `pinForEvent` and the Sandbox's placement-time container drop read - promoted to a core query rather than re-derived per caller. `ignore` skips a Pin *and its whole subtree*: the dragged Pin is the topmost element under its own release point, and it can be dropped neither into itself nor into a descendant. A layout-less DOM has no stack, so there the event's own `target` is the single honest answer.
- **The gesture promotes a move into a reparent only when the scope actually changed.** In `DraggableTrait.onPointerUp`, `target === pin.parent` is the regression lock: a drag ending over open root canvas (both `null`) or back inside its current parent does nothing, so it stays the plain move the last `onPointerMove` already committed. A press that never crossed `DRAG_THRESHOLD_PX` was a click and reparents nothing; a cancelled drag - no event, which is the same convention `cancelDrag` and `onDetach` already used - was not a drop. The point handed to `reparentPin` is the Pin's own current canvas corner, so the drop is visually invisible.
- **Elevation is cleared before the traits are routed, not after.** `setElevationChain` walks `pin.parent`, so stripping `cc-dragging` *after* `onPointerUp` has reparented the Pin would clear the class off the **new** chain and strand it on the old one. The router now clears first and routes second - the order `cancelDrag` already used (§2.10).

### 2.20 Lazy Offload
> `src/engine/offload.js` (the policy and the pass), `src/engine/renderer.js` (phase 0), `src/pins/reload.js` (`resolveRenderMode`).

- **A second axis, orthogonal to `reload`.** `reload: 'lazy'` lazily *creates* a scope's children once, on first visit (§2.5). Offload is the opposite direction on a different question: a Pin flagged `offload: true` whose global box has left the visible canvas has its element detached, and reattached when the camera brings it back. The two compose - a Pin can be `reload: 'lazy'` **and** `offload: true` - because one is about first creation and the other about current DOM membership.
- **Virtualization, not destruction.** Model, particle, traits, contents and cached size are all retained, and no lazy provider is re-armed; that is `unload()`, which is a heavier and separate thing. A reattached Pin re-queues content and measurement through the ordinary MOUNTED path, so it renders *current* state rather than the state it left with - no special-cased under-render.
- **The mechanism is deliberately not new.** The pass raises `pin._offloadDormant`, and `resolveRenderMode` short-circuits on it to `unmounted` *before* the `active` test - because an offloaded Pin is still live in every sense but its DOM membership. Detach and reattach therefore travel the exact same, already-proven structure-flush path a sleeping scope uses (§2.4, §2.5). This pass decides only *when* to raise and lower one flag.
- **Root-only evaluation.** Only root Pins are tested, against their global bounds. Detaching a root's element takes its whole subtree out of the document with it, so nested Pins ride their root rather than being tested one by one. This also sidesteps `ParticleEngine.queryBox`, whose intersection test compares a nested Pin's *local* bounds against a global rectangle - correct for roots, wrong for anything nested.
- **Camera-gated, which is what preserves the idle-canvas guarantee.** The sweep runs as renderer phase 0, and only when the viewport version moved since the last sweep - or when `force` is set, which a newly adopted offload Pin does exactly once so a Pin created off-screen is torn down without waiting for the first pan. A still camera does *no* offload work, so the "an idle canvas performs zero writes" invariant (§2.4) is untouched.
- **The margin is resolved per Pin.** `pin.offloadMargin` (honoured even at `0`, so a Pin can be told to offload the instant it clears the edge), falling back to the session-level `offloadMargin` option, falling back to `DEFAULT_OFFLOAD_MARGIN` (400px). The test is full clearance: a Pin that so much as touches the rectangle grown by the margin is kept. The visible rectangle itself is derived through `viewport.screenToCanvas` - the same projection the pointer router uses - so it is expressed in exactly the coordinates `getGlobalBounds` reports a Pin in.
- **The dirty-cache underneath it was audited, not extended.** Offload's correctness rests on the existing invalidation machinery, so that machinery was re-verified against concrete assertions rather than trusted: an idle frame marks nothing and writes nothing, `invalidate('content')` reaches `_frameDirty` (which is what gates a connector redraw via `isGlobalDirty`), and a Pin invalidated twice in one frame renders once because the dirty collections are Sets. **This was a verification pass. The finding was that the cache is already correct and load-bearing; no new dirty-cache machinery exists, and none was needed.**

### 2.21 The Insert Menu, and the Pin Editor
> `examples/website-sandbox-menu.js` (the commands), `-quicksearch.js` (Shift+A), `-widgets.js` (`insertableItems`), `-editor.js` + `-editor-content.js` (the modal), `-inspector.js` (the quick-panel), `-schema.js` (typed content), `-fields.js` (the form atoms). Application code, stated here because it is the first consumer to use §2.16's registry as its *primary* interface rather than as a garnish.

- **The palette is gone; the canvas's own right-click menu replaced it.** The builder used to carry a sidebar of draggable widget tiles. It now registers an insert *tree* through §2.16's `parent`: one root trigger, `+ New`; one trigger per category in use under it; and one `insert-<item>` leaf per insertable item under its category - every one `when: (s, {pin}) => !pin`, empty canvas only. A trigger carries no action (the registry derives trigger status from being named as a parent); a leaf's action places its item at `session.viewport.screenToCanvas(context.x, context.y, rect)`, so it lands under the pointer at every zoom and pan. This is a strictly better answer to the same question: the sidebar had to be dragged *from* and converted, the menu is already at the destination, and the canvas gets its whole width back. Nothing in `src/` changed to allow the flat menu; the tree needed only the submenu contract the registry now carries.
- **One catalogue, two doors.** Every built-in carries a `category` (*Basic*: the form controls; *Display*: text, badge, avatar, divider, progress, spinner, alert, list; *Layout*: the Container) and every custom type carries one too (§2.22). `insertableItems()` in `-widgets.js` flattens both halves into one list, each entry with the single `place` call that puts it on the canvas, and both the menu's leaves and Shift+A quick-search (`-quicksearch.js`) go through the builder's one `insert(item, point)` command - so neither door owns a copy of the catalogue, and a type saved in the creator is placeable from both at once. Quick-search is a centred native `<dialog>`: substring match on label *and* category, Up/Down wrapping, Enter at the middle of the host box, Escape places nothing; the chord is refused off the Sandbox tab, inside any text field or select, and while another dialog is open.
- **The Pin-scoped half is the same registry, with `when` reading the Pin.** *Edit...*, *Hide chrome* / *Show chrome* (two items whose `when` are complements, because a label is fixed at registration and a single toggling item would have to lie about one of its states), *Detach from container* (only with a `pin.parent`, §2.19) and *Delete*. Each runs the **same function** the editor's own buttons run, handed in as one `actions` object, so Detach-from-the-menu and Detach-from-the-danger-zone are one call site and cannot drift.
- **The registry is a page-wide singleton, so mounting is defensive at both ends.** Registration displaces a stale definition of the same id left by a predecessor that was not torn down (`register` throws on a duplicate id by design, §2.16), and `unmount()` takes every id back. The insert tree is held in a second id set and rebuilt whole by `syncCatalog()` whenever the creator saves or deletes a type - a new category is a new trigger, an emptied one has to go - without disturbing the Pin-scoped items.
- **Two panels, deliberately unequal.** The quick-panel is shallow on purpose - X / Y / Width / Height, *Edit...* and *Delete* - because it floats over the canvas for one selection and a panel that tried to hold everything would be a sidebar again. The editor modal is the complete surface: position and size, chrome and border, traits and reload, contents, and a danger zone. They share `applyGeometry` and `geometryOf` (`-inspector.js`), so both agree on what a write *means*: an axis through `setPosition` with the other two unchanged, a dimension through `resizePin` with a one-pixel floor.
- **Neither panel rebuilds a field the pointer is inside.** Both geometry refreshes skip `document.activeElement`, so typing into X is not fought by the Pin being dragged behind the panel. The editor's `onMutate` also calls the quick-panel's refresh, because they show the same box and a write in one that left the other stale is the panel disagreeing with the canvas.
- **Every control writes through the Pin's public surface, never the particle or the element.** Chrome and border are the live accessors (§2.18). A trait checkbox is `addTrait` / `removeTrait` with membership read from `pin.traits.has(name)`; the resize *options* go through `replaceTrait('resizable', options)`, which is the trait's own detach-and-reattach, because `ResizableTrait` has no in-place option setter. `reload` is a plain writable field the policy reads at the next deactivation (§2.5) - the same write `pin.lazy` makes.
- **`offload` is shown read-only, and that is an honest control rather than a missing one.** The renderer reads `pin.offload` exactly once, when it adopts the Pin (§2.20), and the snapshot does not carry it, so a live checkbox would be a switch that does nothing. It is rendered disabled with the reason beside it. The same goes for `offloadMargin`: the sweep does re-read it per frame, but only for a Pin already in the offload set, which is a set no editor write can join.
- **Contents are typed by a schema, with a generic fallback.** `-schema.js` declares each widget's content keys as text / number / checkbox / enum / list, so a Button's `variant` is a `<select>` of its real variants and a List's `items` is a real list editor with add and remove - not a JSON textarea. A Pin with no schema entry (a Container, a custom type) falls back to a key-value form typed off the *value*, marked `data-content-mode="generic"`. The fallback is what makes every Pin editable, including ones this file has never heard of.
- **The one tradeoff, stated because it is user-visible.** Removing `selectable` from the trait picker closes the click route to that Pin: the builder's selection is driven by the `select` signal, which only a `SelectableTrait` emits, so the Pin leaves the selection set and the quick-panel with it. The right-click route stays whole - the menu resolves `{pin, x, y}` from the click's own element chain and asks no trait anything - so Edit, the chrome toggle, Detach and Delete all still reach it. That is the documented behaviour, and it is locked by a browser test.

### 2.22 Custom Pin Types
> `lib/sandbox/custom-types.js` (the store), `examples/website-sandbox-creator.js` (the "+ New Type" modal), `examples/website-sandbox-widgets.js` (`placeCustomType`).

- **A type is a recipe, not a trait.** `{name, category, fields, traits, chrome, bordered, reload, width, height}` - a name, the insert-menu category it files under (free text, `Custom` when unset, so a type may join a built-in category or coin a new one), the default content fields an instance is born with, the traits to attach, and the appearance and lifecycle defaults. Placing one is `session.createPin(...)` with those defaults spread in plus the trait attachments: exactly the calls a hand-built Pin makes. **Nothing is registered with the trait registry** (§2.3), which is the whole design decision: a page that never loads this module still renders a saved instance, as a card.
- **Its own key namespace, and the reason is enumeration.** `cloudcanvas-custom-type:` rather than `cloudcanvas-sandbox:`. A type is *global* - the visitor made it once and expects it in the insert menu of every profile - so it must not live inside any profile's snapshot; and `listSandboxKeys()` defines "a saved sandbox" as any key under the sandbox prefix, so a type stored there would appear in the Load menu as a profile that cannot be opened. One prefix per concern keeps both enumerable sets honest.
- **`saveCustomType` / `getCustomType` / `listCustomTypes` / `deleteCustomType`, plus `normalizeCustomType` and `customTypeContents`.** Every read normalises on the way out, so a definition written by an older page still loads: an unknown field kind falls back to `text` rather than throwing, an unknown reload strategy falls back to `active`, field keys are de-duplicated first-wins, and traits are filtered to the attachable set. `listCustomTypes` skips an entry that fails to parse rather than throwing - one stale key must not take the whole insert menu down with it - and sorts by name. The storage guard and the `key(i)` enumeration are `persistence.js`'s exactly: no `localStorage` returns rather than throws.
- **The creator's callbacks read `creator.definition` at call time, never a closure over one.** `open()` swaps in a fresh blank definition per opening, so a field callback that captured the definition alive at *build* time would edit an object nobody saves. This is the kind of bug that looks fine in one manual pass and fails on the second opening; it is locked by the browser test that saves a type and asserts the stored JSON exactly.
- **Known limitation: an instance's type identity is not serialized.** `serializeSession` captures trait *names*, and a custom-type instance's traits are the ordinary `card` / `draggable` / `selectable` set - so a snapshot restores it as a generic card. Verified end to end: the restored Pin keeps its position, size, chrome, border and **all of its contents**, is selectable and draggable, and edits through the generic content fallback (§2.21); what it loses is only the label saying which recipe made it. Carrying the identity would mean a `customType` key in the snapshot format and a resolution step on restore, which is a format change and is deliberately not made here.

### 2.23 Child Layout: Flow Containers
> `src/pins/pin.js` (`layout`, `layoutGap`), `src/pins/pin-element.js` (`setLayout`, `syncLayout`, `syncFlowChild`), `src/graphics/styles-css.js` (the four rules), `src/engine/renderer.js` (`_applyPosition`, `clearAppliedPosition`), `src/engine/scope-well.js` (how a flow well is sized), `src/pins/reparent.js` (`reorderChild`, `insertionSiblingFor`), `examples/website-sandbox-layout.js` (the Sandbox's one reader/writer).

- **`pin.layout` says how a Pin arranges its *children*, and nothing about the Pin itself.** `'free'` - the default, and every Pin built before this existed - is unchanged absolute positioning: each child placed by its own transform from its particle. `'row'`, `'column'` and `'grid'` lay the **scope well** out with real CSS flex or grid, and the children flow. Structurally it is the twin of `chrome` (§2.18) one level down: one class, live-settable, mirrored from a flag the Pin holds so a headless Pin still remembers it - but written onto the scope well rather than the root, because that is the box the children sit in. An unknown mode throws a `TypeError` rather than silently staying free. `pin.layoutGap` is the gap in canvas pixels, written as the `--cc-layout-gap` custom property all three modes read; `null` leaves the sheet's own `--cc-space-2`.
- **The child's half of the contract is one class, `is-flow-child`.** `syncFlowChild` puts it on exactly while the Pin has a parent whose layout is not free, and it is called from every path that can change that: `addChild`, `removeChild` (and so `reparentPin` through them), and `setLayout` for each existing child. The class is `position: relative` with `top/left: auto`, and the renderer's `_applyPosition` **declines to write a transform** for such a Pin at all. `relative` rather than `static` deliberately: `z-index` is inert on a static box and both `is-dragging` and `cc-elevated` raise a child through it, so a reorder drag would stop elevating.
- **Crossing the boundary is where the two caches have to be cleared, in both directions.** A `position: relative` box still honours a transform, so entering flow clears the one the Pin wore as a free child - `relative` does not neutralise it. And the renderer's applied-position cache is dropped either way (`clearAppliedPosition`), because on the way *back* to free the transform the Pin now needs would otherwise be skipped as unchanged against a stale entry. With no renderer attached, the leaving-flow write is done synchronously instead.
- **A flow container's well is sized by its own content, not by its children's extent.** `ScopeWellPass` (§2.4's write phase) sizes a free well from `max(child.particle.y + height)` - which is the *only* thing that can size a box full of absolutely positioned children. For a flow child that number describes a position nothing renders at any more: in the Sandbox, the point the widget was dropped at, far down the container. Left alone it inflates the well, and - because the measurement pass writes rendered boxes back into particles - each further child would ratchet it taller still. So the pass writes no `min-height` at all for a flow parent and lets flex or grid size the well, with the sheet's `--cc-scope-min-height` as the only floor. `cc-populated` is unaffected: that is a question about live children, which flow does not change.
- **A flow container places its children and never sizes them.** Each mode states its cross-axis alignment explicitly (`align-items: flex-start` on row and column; `align-items`/`justify-items: start` on grid) rather than taking the browser's `stretch`. This is a correctness rule, not a cosmetic one: a Pin's size is its own, set on the Pin and measured back into its particle, so a stretching flow would silently overwrite every child's height in a row - and its width in a column or a grid - as though the Pin had asked for it.
- **`reorderChild(container, pin, beforeSibling)` is the ordering primitive, and deliberately not a reparent.** The Pin is already a child, so there is no relinking, no renderer re-attach, no coordinate conversion and no well to settle - only order. Two orders move together because two layers read them: the browser paints the DOM, and `Pin.children` is the membership set every other walk of the tree uses. That `Set`'s iteration order *is* insertion order and a `Set` has no insert-at-index, so the order is rebuilt by clearing and re-adding; the element moves with one native `insertBefore`. `serializeSession` (`lib/sandbox/serialize.js`) reads the *DOM* order rather than either model collection - roots off the plane and children off the scope well alike - because the context menu's `bringToFront` / `sendToBack` (§2.16) move only the element, so the DOM is the one place every reorder is recorded. `insertionSiblingFor` turns a drop point into the reference sibling - main axis by mode, midpoint by `getBoundingClientRect`, read live because a flow child's particle x/y no longer says where it is. `DraggableTrait` intercepts the same-parent case ahead of its own no-op guard, so a drop inside the container the Pin already belongs to reorders instead of doing nothing.
- **In the Sandbox it is one editor section and one honest lock.** `website-sandbox-layout.js` is the only reader or writer of `pin.layout` / `pin.layoutGap`; the Layout section is offered to any Pin that can hold children, and the gap row appears only once the mode leaves Free. A child of a flow container has its X and Y **hidden in the editor** with the reason stated, and **disabled in the quick-panel** with the reason as the tooltip - the same refusal the read-only offload rows make (§2.21), for the same reason: a live-looking field that does nothing is a lie. Z and the size stay the Pin's own throughout, and Free hands the axes back.

### 2.24 Windowed Mode, and the Sized Export
> `examples/website-sandbox-frame.js` + `-frame.css.js` (the frame and its controls), `lib/sandbox/export-static.js` (the `page` option).

- **Two ways of looking at one canvas.** *Canvas* is the default and is the infinite plane as it always was. *Windowed* draws a device-sized frame on the plane and flies the camera to fit it - four presets (Mobile 375×812, Tablet 768×1024, Laptop 1440×900, Desktop 1920×1080) or Custom, which reveals a width/height pair opened on the size that was showing. The frame is a **composition guide, not a clip**: Pins outside it are ordinary Pins, and leaving windowed mode takes the frame away and leaves the camera where it is.
- **It is one element on the plane, in canvas space.** Laid out at `left: 0; top: 0` at the device's size, after the focus veil and before every Pin, so the camera transform carries it with no per-frame code, the Pins paint over it, and it inherits the plane's `pointer-events: none` - a right-click on the frame is a right-click on empty canvas. It is anchored at canvas (0, 0) because that is where an exported page's session mounts its camera, so the frame and the exported page's top-left corner are the same point.
- **The mode is not part of the profile.** It is how the canvas is being looked at, not what is on it, so nothing is saved and a reload opens on the canvas.
- **The toolbar cannot wrap, and that is a layout invariant rather than a preference.** A session measures its host box once at mount and again only on a window resize. The view controls come and go as the mode changes, so a toolbar that grew a second row would move the host under a cached measurement and put every screen-space calculation - the context menu's placement, the offload sweep, a drop point - on a stale box. In the full-screen shell the bar is therefore `flex-wrap: nowrap` with `overflow-x: auto` and `flex-shrink: 0` on every control; the right-click hint is the one element allowed to give way, and past that the bar scrolls sideways with its scrollbar hidden so it cannot add height either.
- **`renderStaticHtml`'s optional `page: {width, height}` is the export's half of the same feature**, threaded through `buildStaticSite`, `exportStaticSite` and `downloadStaticSite` unchanged. With no page the mounted root fills the window exactly as before (`position: absolute; inset: 0; width: 100vw; height: 100vh`, `overflow: hidden` on the document). With one it is a box of that size, centred and scrollable (`position: relative`, the size in CSS pixels, `max-width: 100vw; margin: 0 auto`). The viewport meta stays `width=device-width` either way: that is the correct declaration for a page *built* to a device size, and a fixed `width=` would only fight it. A `page` that is given but is not two positive finite numbers throws a `TypeError` - a caller that meant to size the page and mistyped it must not silently get a window-filling one.
